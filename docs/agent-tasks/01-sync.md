# Задание: движок синхронизации (M3 + M4)

> Вставь перед этим текстом `00-CONTEXT.md`.

**Это критический путь проекта.** ТЗ прямо говорит (§14): ошибка в модели данных
здесь означает переписывание, а не доработку. Остальное аддитивно, это — нет.
Не торопись с кодом, сначала спроектируй.

## Что построить

`pkg/sync` (движок) и `pkg/remote` (транспорты) по §8, плюс команды
`binpass sync`, `binpass remote`, `binpass conflicts`.

## Порядок работы

### Шаг 1. Модель данных и разрешение конфликтов — до всякого транспорта

Начни с `pkg/sync` в вакууме: version vectors, определение расхождения,
классификация конфликтов. Транспорт подключишь потом.

`FileState` описан в §8.1. Хеш берётся от **шифротекста** — это позволяет
синхронизировать заблокированный стор. Но GPG недетерминирован: перешифровка
того же plaintext даёт другой шифротекст, поэтому первичный детектор изменений —
`(size, mtime)`, а хеш подтверждает. Не перепутай порядок.

Таблица решений — §8.5. Разбери каждую строку:

| Ситуация | Действие |
|---|---|
| VV равны | ничего |
| Локальный доминирует | push |
| Удалённый доминирует | pull |
| Расходятся | конфликт |
| Расходятся, шифротексты идентичны | слить VV, файл не трогать |
| Расходятся, в секрете HOTP | автомерж по `max(counter)` |
| delete vs edit | побеждает edit + warning |

HOTP — единственное место, где движок заглядывает **внутрь** секрета, и это
неизбежно: счётчик расходится на двух устройствах закономерно. Используй
готовый `pkg/otp`. Для всего остального движок работает с непрозрачными
байтами.

Дефолт при конфликте — обе копии на диск, ничего не теряется молча:
```
github.com/alice.gpg                                    ← удалённая
github.com/alice.conflict-thinkpad-20260808T142233.gpg  ← локальная
```
Конфликтные файлы шифруются **теми же получателями** (§10), иначе утечка.

**Автомержа полей нет.** Слишком легко получить секрет-франкенштейн с логином
от одной версии и паролем от другой.

**Property-тесты обязательны** (§12): «ничего не теряется» и детерминизм при
любом порядке аргументов. Прогоняй мерж на случайных парах состояний и
проверяй инварианты. Это дешевле, чем отлаживать потерю данных у пользователя.

### Шаг 2. Состояние и надёжность

`sync/state.db` на bbolt в `$XDG_DATA_HOME/binpass/` — **вне стора** (§1).
Если состояние попадёт в стор, оно уедет в git-историю и на Google Drive, а
`pass git status` будет показывать мусор.

WAL реигрывается при старте, если процесс убили посреди операции (§8.6).
Напиши тест, который реально убивает операцию на середине и проверяет
восстановление.

`binpass fsck` сверяет дерево, state.db и recipients, чинит расхождения.

### Шаг 3. Интерфейс транспорта и git

`Remote` описан в §8.2. `Caps()` возвращает возможности: Atomic, History,
Locking, Rename, Watch — движок подстраивается.

Первый транспорт — **git** (§8.3):
* Системный `git` через exec (credential helpers, ssh-agent, подпись коммитов,
  прокси работают сами), `go-git` — фолбэк.
* Сообщения коммитов **те же, что у pass**: `Add given password for X to store.`
  История должна быть неотличима. Посмотри исходник pass, не выдумывай.
* Должен работать с любым существующим pass-репозиторием без конвертации.

### Шаг 4. Облака

rclone как **библиотека**, точечные импорты `drive`, `yandex`, `webdav`, `s3`
(§8.4). Не `backend/all` — бинарь распухнет на десятки мегабайт. Полный набор
под build-tag `rclone_full`.

Встроенный OAuth: `binpass remote add gdrive` поднимает локальный редирект на
`127.0.0.1`, открывает браузер, кладёт токен в `remotes.age`. Для headless —
device-flow с кодом. Существующий `~/.config/rclone/rclone.conf` подхватывается,
если есть.

Что реально стреляет:
* **Атомарности нет нигде.** S3 — `If-Match` по ETag. Drive/WebDAV/Yandex —
  advisory-lock `.binpass.lock` с TTL и владельцем + verify-after-write.
* **Rate limits.** Drive: 1000 запросов/100 с. Backoff с jitter, батчинг,
  уважение `Retry-After`. **Дельта-синхронизация обязательна** — стор на 2000
  записей нельзя лить по файлу за запрос.
* **Drive допускает два файла с одинаковым именем в папке.** При дубле не
  угадывай — зови конфликт-резолвер.
* Yandex.Disk доступен и как WebDAV, и нативно. Нативный по умолчанию.

## Тесты

Без этого работа не принимается:
* Property-тесты движка мержа (см. выше).
* Интеграционные на `testcontainers`: bare git, WebDAV, MinIO, `rclone serve`
  как заглушка Drive. Сценарий: **два клиента, оффлайн-правки, конфликт,
  разрешение** — это критерий готовности M3 из §14.
* Тест на прерывание посреди записи → WAL восстанавливает.
* Тест, что state.db не появляется внутри стора ни при каком сценарии.
